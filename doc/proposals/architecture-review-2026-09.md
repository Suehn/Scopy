# Scopy 全仓架构评审（2026-09）

基线：`607404e`（v0.78.0）。六个独立评审（采集语义、存储/去重/格式、搜索、Markdown 预览与导出、UI/交互/设计、并发/稳定性/代码结构）逐文件读代码得出，候选结论附 `file:line`，行号以该 commit 为准。数据库事实来自仓库内真实快照 `perf-db/clipboard.db`（9,566 条，146 MB）。候选结论仍须在实施前复现；下面的主线程裁决优先于原始评审判断。

## 0. 怎么用这份文档

- 每条方向 = 问题 + 证据 + 方向 + 验收 + 规模（S ≤ 半天，M 1–3 天，L 一周以上）。Codex 一次只做一条；不要把多条合进一个改动。
- 硬约束（hh 的 7 条 + `CLAUDE.md`）：不保留向后兼容层、fallback 或 migration；过时路径直接删除；发现死代码直接删，不 flag 化；先用项目已有依赖。
- 优先级：**P0** = 数据安全、隐私、静默失败、核心交互缺失；**P1** = 可测量的性能/内存问题、语义不一致；**P2** = 结构收敛、设计打磨。
- 文中"现状事实"是评审读代码的结论，不是用户反馈；实施前 Codex 应先按 `file:line` 复核一遍，行号漂移以代码为准。

### 0.1 v0.78.1 主线程裁决（2026-09-03）

- **实施**：隐私标记整次采集跳过；搜索单条证据无法构建时保留结果并降级为普通元数据行。
- **否决**：§6.1 的 `</head>` P0 在未改动的基线无法复现。默认 `JSONEncoder` 将 Markdown 源里的 `</head>` 编码为 `<\/head>`，原注入逻辑只会命中真实结束标签；不得为了复现而启用 `.withoutEscapingSlashes`。
- **暂缓**：§8.1 事件流重订阅缺陷属实，但当前没有正常的同进程 stop→start 产品入口，且与异步停止竞态耦合；与生命周期设计一起处理。
- **暂缓**：§8.2 正常退出未等待异步 close 属实，但不破坏已提交 WAL 的 D1 保证；`.terminateLater` 会影响退出体验，并需要启动竞态、超时、幂等与 Sparkle 重启测试，不纳入三小时安全修复批次。
- **不批准迁移方案**：下文涉及 schema、哈希公式或存储布局的 migration 描述是 Claude 的原始候选，不符合当前“删除旧路径、不做迁移”的工程约束，不能直接执行；未来若选中相应问题，必须先重新设计为只保留当前模型的完整方案。

## 1. 七个跨模块主题

1. **静默失败**：搜索证据构建失败会清空整页结果（§5.1）；复制/删除/置顶/备注失败只写日志（§7.4）；正则无效等同"无结果"（§5.3）。共同方向：任何失败都要有一个用户可见的落点，且失败降级为"少一点信息"，不是"什么都没有"。原先关于 `</head>` 导出的判断已由 §0.1 否决。
2. **文本的一次规范化、两份文本**：采集时 `normalizeText` 修剪首尾、替换 NBSP，破坏粘贴保真（§3.2）；去重哈希不做 NFC（§4.2）；搜索引擎按 UTF-8/UTF-16 比、证据按 grapheme 比（§5.1）。共同方向：原文只存一份、原样回贴；规范形（NFC + 折叠）只算一次，哈希、索引、证据全用它。
3. **无上限项**：`plain_text` 单行可达 1 MB 且永不外置；fuzzy 索引把全语料小写副本常驻内存；trigram 索引 39.9 MB 对应 19.5 MB 正文；`ThumbnailCache` 只限数量不限字节；导出 hover 图片缓存 320 MB（§4.3、§5.4）。共同方向：每一处都给出明确上限和退化行为。
4. **核心交互差一步**：无 ⌘1–9、无开机自启、无撤销删除、悬停会偷走键盘选中（§7.2）。这些不是性能问题，但对"像不像一个成熟剪贴板工具"影响最大。⏎ = 复制并关闭面板是 hh 的既定设计，不在此列。
5. **双实现与死代码**：`extractContent` 旧路径、`cleanupThumbnailCache`、`performWALCheckpoint`、`incrementalVacuum`（空操作）、`SearchPlanner`（只用于日志）、两套 WebView 生命周期、Swift/JS 各一份 table-pipe 规范化、三个"文件是否被引用"谓词、三处 ⌥⌫ 注册、两个字节格式化器、两个"加载更多"入口。方向：列清单逐条删。
6. **语言与遥测**：主面板英文、设置全中文、行元数据和搜索证据中文，无任何本地化基础设施；"Recent" 段头和 About 页把性能/ingest 遥测直接展示给用户。
7. **生命周期没有闭合**：事件流取消后永久死亡（§8.1）；正常退出未等待 best-effort 的缓存持久化与 checkpoint 尝试（§8.2）；无睡眠/唤醒、显示器变化、内存压力处理；WebKit 进程从启动常驻（§8.6）。这些是后续生命周期设计候选，不代表已提交 WAL 数据不安全。

## 3. 采集与语义（`ClipboardMonitor`、`ClipboardService`）

### 3.1 隐私标记（P0，S）

现状：采集不读取 `org.nspasteboard.ConcealedType`、`org.nspasteboard.TransientType`、`org.nspasteboard.AutoGeneratedType`，也不识别 `com.agilebits.onepassword`。密码管理器复制的密码会明文进入 `clipboard_items.plain_text` 与 FTS。

方向：在 `ClipboardMonitor` 读取 pasteboard 类型列表的位置一并检查这四类标记，命中即跳过整个 changeCount。不做"可配置白名单"，这是 macOS 生态的既定约定。

验收：单测用命名 pasteboard 写入带 `ConcealedType` 的文本，断言不产生条目；`make perf-capture SCENARIO=text` 不回归。

### 3.2 原文与规范文本分离（P0，M；与 §4.2、§5.2 联动）

现状：`normalizeText`（`ClipboardMonitor.swift:2466-2478`）做 U+2028/2029/0085 → `\n`、NBSP → 空格、去 BOM、`trimmingCharacters(.whitespacesAndNewlines)`、CRLF → LF，然后这份文本既用于哈希，也用于 `plain_text`，也是纯文本条目回贴时的来源（`payload: .none`，`:1925`）。结果：复制 `"  foo  "` 回贴得到 `"foo"`；含 NBSP 的代码回贴后空格类型改变。不做 NFC。

方向：

- 纯文本条目保存原始字符串（作为 payload 或单独列），回贴一律用原文。
- 规范形只算一次：NFC + 换行统一 + 大小写折叠（可选 diacritic 折叠），用于 `content_hash`、FTS/内存索引、搜索证据。`plain_text` 列存规范形供展示与搜索。
- 搜索证据构建器（§5.1）与引擎共用同一个规范化函数。

验收：回贴保真单测（前后空白、NBSP、CRLF、U+2028 原样）；`SearchMatchContextBuilderTests` 增加 NFD 用例覆盖 fuzzy 与 `instr` 路径；`make test-unit`。

### 3.3 采集稳定性（P1，M）

- **自粘贴竞争**：`lastChangeCount` 在 `await` 之后可能已过期，Scopy 自己写 pasteboard 后有概率把自己的写入再采集一次。方向：写 pasteboard 时记录预期 changeCount，采集循环遇到该值直接跳过；不要用"内容相同就忽略"的启发式。
- **单次读取与大小上限**：同一 changeCount 对多个类型各读一次；没有最大采集大小。方向：一次 `types` 枚举 + 一次读取；加可配置上限（默认建议 32 MB），超限跳过并记录。
- **轮询**：固定间隔（设置 100–2000 ms）。方向：前台空闲时退避到较长间隔，`NSWorkspace.sessionDidResignActive` / 锁屏时暂停。
- **文件条目**：目录 URL 没有 `isDirectory` 守卫；无 security-scoped bookmark，文件被移动后回贴失效。方向：目录明确处理（可复制路径、不可回贴文件内容）；对 `.file` 存 bookmark data。
- **启发式**：TAB 分隔文本误判为表格；`<img` 提前返回；PDF/SVG 不读；GIF 被扁平化成 PNG；RTFD 丢失。方向：这些是产品范围决策，逐项决定"支持"或"明确不支持"，不要留半成品分支。
- **死路径**：`extractContent` 与 `extractRawData` 并存，前者已无生产调用。删。
- **ingest 回放**：启动时回放 `ingest/` 目录不按 mtime 排序；连续崩溃后条目顺序可能倒置。方向：按 envelope 时间排序回放。
- **缩略图 40 px**：`thumbnailHeight` 直接作为像素传给 ImageIO，2× 屏上是 40 px 不是 40 pt（`StorageService.swift:2347-2353`）。方向：乘 `backingScaleFactor`，并同时限宽（§4.3）。

### 3.4 Codex 回贴路径的权限守卫（P1，S）

现状：⏎ = 复制并关闭面板是既定设计，保持不变。唯一会主动发键盘事件的动作是右键菜单"Paste optimized for Codex"，发 ⌃V（`AppDelegate.swift:324-348`），无 `AXIsProcessTrusted` 检查，无辅助功能权限时事件被静默丢弃，面板已关闭，用户看不到任何反馈。

方向：发事件前检查 `AXIsProcessTrusted()`，无权限时不发事件、只完成复制，并用 §7.4 的 toast 提示一次"需要辅助功能权限"并给出打开系统设置的入口。不扩展成通用粘贴服务。

## 4. 存储、去重、保留、格式（`SQLiteClipboardRepository`、`StorageService`）

### 4.1 表结构与大小（P1，L）

现状（真实快照）：`clipboard_items` 92.2 MB，其中内联 `raw_data` 68.0 MB、`plain_text` 19.5 MB；`clipboard_fts_trigram_data` 39.9 MB；`clipboard_fts_data` 8.4 MB；九个索引共约 4 MB。`plain_text` 永不外置，20 行超过 100 KB，最大 1,014,052 字节（`ClipboardMonitor.swift:1925`；`StorageService.swift:519,543` 的外置规则只作用于二进制载荷）。`id` 为 UUID 字符串主键。

方向（分两步，第一步独立可交付）：

1. 加 `preview_text`（规范形前 8 KB），列表、FTS、trigram 只用它；全文留在 `plain_text`。采集加硬上限（建议 4 MB，超限截断并在行元数据标注）。这一步直接把 trigram 表缩到一小部分，并给 §5 的内存上限提供列。
2. 若之后仍需要：把载荷列拆出 `items` 主表（元数据 + preview）与 `item_text` / blob 侧表，列表查询不再经过载荷页。整型 rowid 主键 + UUID 唯一二级键。这一步只有在第一步后仍有可测量的列表/页缓存问题时才做。

验收：迁移后 `perf-db` 快照的文件大小、`clipboard_fts_trigram_data` 大小前后对比进 release-runbook；`make test-snapshot-perf-release` 搜索延迟不回归。

### 4.2 去重（P0，M）

现状（`ClipboardMonitor.contentHash`，`ClipboardMonitor.swift:1789-1824`）：`.text/.rtf/.html` 共用 `sha256(normalizedText)`，所以先复制纯文本 `foo` 再从 Word 复制带格式的 `foo`，后者被折叠为前者的一次使用，RTF 载荷被丢弃、用户永远贴不出富文本。NFC/NFD 视为不同内容。`.file` 只哈希路径：同一路径换了内容会被错误去重，文件改名会产生重复。TIFF → PNG 依赖 ImageIO 编码器，pngquant 设置变化会改变同一图片的哈希并留下孤儿缩略图。`content_hash` 无 UNIQUE。

方向：

- 哈希公式 = `sha256(type_namespace ‖ canonical_bytes)`。纯文本 = NFC 规范文本；rtf/html = 类型 + 规范文本 + 原始载荷；图片 = 原始载荷（保持现状）；文件 = 路径 + 每个文件的 `(size, mtime)`。
- 一步前向迁移：对 text 族行重算哈希（全部内联，成本低）；图片/文件行公式不变，无需重算。不加 `hash_version` 列——这是没有当前消费者的推测性设计，将来再改公式就再迁移一次。
- `content_hash` 加 UNIQUE 索引，非 ingest 路径的"先查后插"改为 `INSERT ... ON CONFLICT DO UPDATE`，关掉 TOCTOU 窗口。

验收：去重单测覆盖（纯文本 vs 同文富文本不折叠；NFC/NFD 折叠；同路径不同内容不折叠）；迁移在 `perf-db` 快照上跑一次并核对行数不变。

### 4.3 内存与列表路径（P1，S 与 S/M）

- 列表分页 `fetchRecent/fetchPinned/fetchRecentUnpinned` 的 SELECT 带 `raw_data`（`SQLiteClipboardRepository.swift:562-618`），每页解码 0.7–15 MB blob 后丢弃；无 blob 的 `fetchRecentSummaries` 已存在但只有搜索引擎在用（`:620-653`）。方向：列表路径切到 summary 查询。**S，零风险，先做。**
- `planCleanupByTotalSize`（`:1071-1108`）无 LIMIT 的 `ORDER BY last_used_at ASC` 扫描跑在唯一写连接上。方向：加 LIMIT 分批。S。
- `ThumbnailCache` NSCache `countLimit = 1000`、无 `totalCostLimit`；缩略图只限高不限宽（`StorageService.swift:2347-2353`），全景图会生成 4000×40。方向：`totalCostLimit`（建议 64 MB）+ `maxPixelSize` 同时约束宽高。S。
- `HoverPreviewImageCache` 320 MB / 单项 256 MB（v0.78.0 上调）。方向：回到 160 MB / 128 MB，并用 `NSCache` 的内存压力回调；hover 预览没有理由常驻 320 MB 解码位图。S。
- `ClipboardItemContentRevision.memo` 8192 项各持有整段 `plainText`。方向：memo 只存 hash 和字段指纹，不持有文本。S。

### 4.4 持久性与恢复（P0，M）

现状：`incrementalVacuum` 是空操作（从未设 `auto_vacuum=INCREMENTAL`，且门槛是 WAL > 128 MB，默认 autocheckpoint 下达不到）；`performWALCheckpoint()` 生产从不调用，唯一的 checkpoint 在 `close()`，而退出走的是 detached Task（`RealClipboardService.swift:36-40`），进程通常先退出；无 `integrity_check`；无备份/导出/导入；`writeAtomically` 无 fsync，envelope 不记载荷校验和，断电后撕裂的载荷会被回放为合法条目。

方向：

- 一次性 `VACUUM` 迁移 + `auto_vacuum=INCREMENTAL` + `journal_size_limit`；面板关闭 / 空闲时调用 checkpoint（PASSIVE）；删掉 128 MB 门槛。
- 启动时节流的 `PRAGMA quick_check`（每周一次或 mutation_seq 跨阈值时），失败进入 `StartupFailureView` 并提供"从备份恢复"。
- 备份 = `sqlite3_backup` 快照 + `content/` 目录 + schema 版本号，写到用户选定位置；恢复 = 反向。这是产品级功能，UI 入口放在 Storage 设置页。
- ingest envelope 加载荷 sha256；回放时校验，不匹配则丢弃并记录，不入库。
- `writeAtomically` 用 `Data.write(options: .atomic)` 或显式 `fsync`。

验收：`StorageCommitProtocolTests` 扩展撕裂载荷用例；备份/恢复往返测试在 `perf-db` 快照上行数与哈希集合一致。

### 4.5 并发边界（P1，M）

现状：`StorageService` 标 `@MainActor` 但不碰 AppKit；每次存储调用是 `ClipboardService actor → MainActor → repository actor` 两跳；清理阶段在主线程逐文件 `fileExists`/`attributesOfItem`（`StorageService.swift:1130-1153, 2237-2277`）；写 repository 每次 `sqlite3_prepare_v2`（`:1518-1525`），无语句缓存；`busy_timeout` 500 ms。

方向：`StorageService` 改为 `actor`（或拆为 nonisolated 静态助手 + 一个小的发布协调 actor）；repository 镜像 `SearchEngineImpl` 的 LRU 语句缓存；列表与统计读迁到 `query_only` 只读连接，写连接只服务写与清理计划；`busy_timeout` 提到 3–5 s。ref-count / generation 守卫必须留在同一 executor 上。

验收：`make test-strict`、`make test-tsan`；`make perf-capture SCENARIO=rich` 主线程等待时间不回归。

### 4.6 保留策略（P1，M）

现状：`total_size_bytes` 包含外置字节（快照里 1,009 MB 总量、838 MB 外置、文件本身 146 MB），200 MB "内容预算"实际上是删图片的触发器；`maxLargeStorageMB = 800` 硬编码且不可见；缩略图从不随条目删除，`cleanupThumbnailCache` 零调用；`ingest_receipts` 只在 ack 时删除，无按时间回收；10,000 条全 pinned 时清理会空转。

方向：小预算只计内联字节；800 MB 外置上限暴露到设置；条目删除事务内同步删除其缩略图（按 `content_hash` 引用计数）；`ingest_receipts` 按 `committed_at` 回收（索引已存在）；清理计划遇到"全部 pinned"时明确退出并记录。

### 4.7 格式与可移植性（P2，S + L）

- TIFF 转 PNG 失败时原样存 TIFF，但文件名固定 `.png`（`ClipboardMonitor.swift:2951-2962`、`StorageService.swift:2223`）。方向：转换失败即按 `.other` 处理或拒绝，不制造错误后缀。S。
- `storage_ref` 存绝对路径，库不可搬迁；三个"是否被引用"谓词（basename 集合 / 精确路径 / `LIKE '%/basename'`）判断不一致，搬迁后会出现"文件保留但载荷加载失败"。方向：存相对根目录的路径，读取时拼接；三个谓词合一。S。
- 外置文件内容寻址（`content/<hh>/<sha256>` + refcount）、载荷压缩列（LZFSE，HTML/RTF 5–10×）。这两项价值真实但改动触及孤儿清理协议（最安全关键的代码），放 P2，且必须用现有 interlock 测试钩子驱动。L。

明确不要动的：ingest/receipt exactly-once 协议与 plan-then-revalidate 删除协议的不变量。

## 5. 搜索（`SearchEngineImpl`、`SearchMatchContextBuilder`、`HistoryViewModel`）

### 5.1 证据缺失导致整页失败（P0，S）

现状：`SearchEngineImpl.swift:1867-1875` 与 `ClipboardService.swift:1081-1085` 在任一结果行无法构建 match context 时 `throw`；`HistoryViewModel.swift:1115-1124` 捕获后 `clearSearchProjection()`，列表清空、无错误提示。引擎按 UTF-8 字节（`instr`/`LIKE`）或 UTF-16（`fuzzyMatchScoreASCIIUTF16`）匹配，证据按 `Character` 或 `NSString.range(of:)`（无 `.literal`）比较。已验证：NFD 的 `Café.txt`（Finder 复制得到）用 `cafe` 搜，引擎命中、证据失败、整页消失。

方向：证据缺失的行按普通元数据行渲染并计数上报，不抛错；根因由 §3.2 的统一规范化解决。两者分开交付，前者先做。

### 5.2 模式间折叠不一致（P1，随 §3.2）

现状：七条匹配路径七种折叠（FTS 去音标、`localizedCaseInsensitiveContains` 区域相关、`lowercased()` 不去音标、SQLite `lower()` 仅 ASCII、`instr` 大小写敏感、`LIKE` 仅 ASCII、trigram 保留音标）。`cafe` 在 Exact 能找到 `café`、在 Fuzzy+ 找不到。

方向：所有路径读同一个规范形列（§4.1 的 `preview_text` / 规范化 `plain_text`），SQL 侧 `instr` 直接在规范形上比，去掉 `lower()`。

### 5.3 错误可见性与安全包络（P1，M）

- 无效正则、超时、refine 失败三者都表现为空列表。方向：`searchCoverageHint` 已有的那一行（`HeaderView.swift:58-64`）显示错误文案。S。
- 正则无长度/复杂度限制，5 s 超时只能 `sqlite3_interrupt`，对纯 Swift 的正则与 fuzzy 扫描无效，且 actor 被阻塞后后续搜索排队；正则在证据阶段对每行再跑一次、编译两次。方向：查询长度上限（建议 512）、正则在 detached task 上带独立 deadline 运行、编译一次两处复用。M。
- 正则不 trim，单个空格是合法正则匹配几乎所有行。方向：与其他模式一致地 trim。

### 5.4 证据生成成本（P1，M）

现状：每次按键为 50 行各构建证据，在搜索 actor 上串行；exact ≥3 对每行整段 `plain_text` 用 SQLite unicode61 tokenizer 分词（`SearchMatchContextBuilder.swift:864-935`）；`Unicode61Tokenizer()` 每次请求新开内存 SQLite 库并解析 fts5 API（`:143-224`）；regex 与 ≤2 字符 exact 构造 tokenizer 后从不使用（`:397-399`）；长文档 exact p95 ≈ 99 ms 几乎全是这一段。

方向：tokenizer 进程内复用；dead work 分支删除；证据只扫描规范文本前 N KB（与 §4.1 preview 列一致）；证据构建移到搜索 actor 之外的并行任务，引擎只返回 id 与分数。

验收：`make test-snapshot-perf-release` 长文档 exact p95；`make perf-search-type` 主线程 sample 中证据构建占比。

### 5.5 排序模型（P1，M）

现状：所有六处比较器 `is_pinned DESC` 硬排第一；FTS `bm25` 未加权（note 短天然占优）；fuzzy 分数是紧凑度启发式不归一化；substring 路径按"最小字节偏移"排；`useCount`、`createdAt` 从未参与排序；recency 只做平局项。

方向：`bm25(clipboard_fts, 10.0, 1.0)`；fuzzy 与 substring 比较器加 `exp(-age/τ)`（τ ≈ 3 天）与 `log1p(useCount)`；前缀/整词匹配加分；pinned 改为大额加分而非硬排序键。所有权重集中在一个 `SearchRanking` 类型，不散落六处。

验收：排序 golden 测试（"每天都复制的那条"在弱匹配的 pinned 之上）；`make test-snapshot-perf-release`。

### 5.6 索引结构（P2，L；先 spike）

现状：三套结构（`clipboard_fts` unicode61、`clipboard_fts_trigram`、`FullFuzzyIndex` 字符 postings + 全语料小写副本、`ShortQueryIndex` bigram），加两层 staged refine。`FullFuzzyIndex` 在 10k 条约 25–90 MB，100k 条无上限；按字符 AND 的候选过滤太弱（≥6000 候选是常态），这正是第二层 staged 存在的原因。`SearchPlanner` 的决策树只用于日志，真实分支在 `searchExact/searchFullFuzzy` 各写一遍。

方向：先做 §4.3/§5.4 的上限（S/M），测量后再决定是否用一套规范语料上的 2/3-gram postings 替代 `FullFuzzyIndex` 与 `ShortQueryIndex`，幸存候选从 SQLite 回读文本打分。spike 门禁：在 `perf-db` 上同一查询集的召回一致、p95 不劣、常驻内存下降。同时删除只用于日志的 `SearchPlanner` 复制品。

### 5.7 refine 与分页交互（P1，M）

- `replaceSearchPage(skippingIdenticalRefine:)` 的相同判定包含 `total`，refine 时 `total` 从 -1 变成 N，守卫几乎从不生效（`HistoryViewModel.swift:1518-1523`）。
- 用户翻过第一页后 refine 直接跳过（`:1070, 1100`），第 2 页起永远停在 prefilter 语义而 pill 仍显示"Calibrating"。
- staged 结果 load-more 用 `offset: 0, limit: loadedCount + 100` 整体重跑并替换，滚动越深成本越高，行会重排消失。
- refine 落地时选中行不在新页就丢选中。
- 偏移分页在新条目插入时错位一行；无 keyset。
- 搜索模式不持久化而排序持久化；Fuzzy+ 对 ASCII ≥3 字符是子串匹配，比 Fuzzy 更严，与"+"暗示相反。

方向：相同判定忽略 `total`；翻页后仍 refine；按 id 保留选中；load-more 用 keyset（`last_used_at, id`）；持久化模式；Fuzzy+ 要么改成 Fuzzy 的超集要么改名。

## 6. Markdown 预览与 PNG 导出

### 6.1 `</head>` 导出判断已否决

复核结果：未改动基线的默认 `JSONEncoder` 会把 Markdown 源中的 `/` 转义，正文与 fenced code 里的 `</head>` 均以 `<\/head>` 存入脚本 JSON；整份文档唯一原样 `</head>` 是真实 head 结束标签。因此现有注入查找不会被用户 Markdown 抢先命中。

结论：不增加显式 slot，不改变 JSON 编码策略，也不破坏现有 raw-HTML 导出入口。若未来发现真实失败，必须先提供在未改动发布基线可复现的 fixture，再重新设计。

### 7.7 固定预览（hh 需求，P1，M）

需求：有时需要长时间阅读预览内容，不想一直把指针停在行或 popover 上；希望能把当前预览"固定"住，读完再手动关闭。

现状约束：预览是行锚定的 SwiftUI `.popover`（`HistoryItemView.swift:1037-1164` 三处），列表层只维护一个 `activePopover`（`HistoryListView.swift:41, 330-442`）；关闭由指针离开行/popover（`scheduleRowHoverExitCleanup`、`schedulePopoverHoverExitCleanup`，120 ms 宽限）、滚轮（`dismissPreviewForScrollWheel`）、系统 dismiss、以及产品规范里的安全三角 500 ms 上限共同驱动；行是被动的，交互状态在空闲时释放（`releaseInteractionStateIfIdle`），行回收时 popover 随之消失；Markdown 只有一个共享 `WKWebView`（ownership lease）。所以"固定"不能只是把 hover-exit 计时器关掉——行一滚出视口或被回收，锚点就没了。

方向：

- **固定 = 把预览从行提升到列表/面板层**。新增一个由 `HistoryViewModel`（或列表层协调器）持有的 `pinnedPreview: (itemID, kind, revision)`，内容宿主是面板的一个子窗口（`NSPanel` child window，非激活、跟随主面板移动），不再是行锚定 `.popover`。触发时把当前 hover 预览的已渲染状态（`HoverPreviewModel`、Markdown 的 WebView lease、图片位图）整体移交给它，不重新渲染。
- **触发与关闭**：预览打开时按 Space 或点 popover 顶部的图钉按钮固定；关闭只靠显式动作：⎋、图钉再点一次、子窗口关闭按钮、面板关闭。不做自动超时。滚动、指针离开、行回收、hover 其他行都不关闭它。
- **与 hover 的关系**：同一时间只允许一个固定预览；固定期间 hover 预览停用（避免两个预览并存，也避免抢 Markdown 的唯一 WebView）；再次固定另一行 = 替换。固定预览的条目被删除或同 ID 内容替换（规范 `:145`）时关闭。
- **与其他条目的联动**：§7.3 `resignKey` 不能因为焦点进入固定预览子窗口就关掉主面板；§8.6 的 WebView 延迟释放要把固定预览视为"在用"；`HistoryListInteractionCoordinator` 的 scroll 抑制不得撤销固定预览的所有权（它不再是 hover 候选）。
- 键盘：固定预览内 ⌘+/⌘− 调 Markdown 缩放（复用现有 80–200% 滑块的模型），↑↓ 仍在列表里移动选中但不改变固定内容。

验收：固定后滚动列表、hover 其他行、指针移出面板，预览保持；⎋ 关闭；删除该条目后自动关闭；`HistoryListUITests` 增加"固定后滚动不关闭"与"⎋ 关闭"两条；`make perf-scroll-wheel` 在有固定预览时不回归。

## 8. 并发、稳定性、生命周期、代码结构

### 8.1 事件流在取消后永久死亡（P1，M，暂缓）

现状：`ClipboardService.eventStream` 在 `init` 里用 `AsyncStream(unfolding: { await queue.dequeue() })` 创建一次、`nonisolated let`（`ClipboardService.swift:856-858`）；`ClipboardEventQueue.dequeue()` 在 `Task.isCancelled` 时返回 `nil`（`:480-499, 535-539`）；`AsyncStream(unfolding:)` 第一次得到 `nil` 即永久终止。`AppState.stop()` 会 `eventTask?.cancel()`，之后 `start()` 重新迭代同一条已死的流。结果：任何 stop → start 之后后端正常、UI 永远收不到新条目/删除/设置变更事件，无任何报错。`ClipboardMonitor.contentStream`（`:342-344`）同构，只因每次 `start()` 新建 monitor 才没暴露。

方向：改为 `func events() -> AsyncStream` 每个订阅者一条新流，或让 `dequeue()` 区分"取消"与"结束"。加 stop → start → 收到事件的回归测试。

### 8.2 退出路径不确定（P1，M，暂缓）

现状：`applicationWillTerminate` → `AppState.stop()` → `RealClipboardService.stop()` 是 `Task { await clipboardService.stop() }` fire-and-forget（`RealClipboardService.swift:36-39`），进程随即退出。本该执行的 `ClipboardService.stop()`（`:996-1033`）里包括 `storage.close()`（WAL checkpoint + `sqlite3_close`）与 `search.close()`（`SearchEngineImpl.swift:1004-1016`，持久化短索引与全索引磁盘缓存）。后果：磁盘缓存只在从 DB 全量构建后写一次，此后每次采集都让它 stale，正常退出又不落盘，所以每次启动都是 stale 命中——这与 v0.78.0 测到的"短索引缓存 stale"一致；`performWALCheckpoint()` 只有测试在调（`PerformanceTests.swift:572-672`）。

方向：`applicationShouldTerminate` 返回 `.terminateLater`，`await service.stopAndWait()`（已存在，`RealClipboardService.swift:41-43`），带硬超时（建议 3 s）后 `reply(toApplicationShouldTerminate:)`。与 §4.4 的 checkpoint 调度一起交付。

验收：退出后 `clipboard.db.shortindex.*.bin` mtime 更新；下次启动日志出现 "disk cache load hit"。

### 8.3 `Runtime/` 编进两个模块（P1，S）

现状：`Package.swift:14-33` 与 `project.yml:59-72` 的 exclude 列表都没提 `Scopy/Runtime/`，所以 `PerfFeatureFlags.swift` 与 `ScrollCursorSetCoalescer.swift` 同时编进 ScopyKit 和 Scopy/ScopyTests/ScopyTSanTests（`project.pbxproj:149,191,496` 与 `:68,309,635`）。两个 `internal` 的 `PerfFeatureFlags` 类型各自求值 `static let`。

方向：`Runtime/**` 只属于一个模块（放 ScopyKit 并 `public`）；模块边界改为按目录而不是两份手写 exclude。

### 8.4 feature flag 与死路径（P1，M）

- `PerfFeatureFlags` 11 个 flag 全部默认为发布行为，`false` 分支只为同一二进制 A/B 存在；`passiveHistoryRowEnabled` 还养着整条 legacy eager-observer 行路径（`HistoryItemView.swift:376`、`HistoryListInteractionCoordinator.observe/notifyLegacyObservers:232,450`、`HistoryListInteractionObservation.swift`）；`cleanupShadowCompareEnabled` 默认 false 纯诊断。方向：按 hh 第 1 条全部删除，每删一个跑一次 `make perf-frontend-profile` 重新基线。
- `readCurrentClipboard()` → `extractContent` → `extractOptimalImageData`（`ClipboardMonitor.swift:493, 1828-1947, 2946`）生产零调用，只有 `ClipboardMonitorTests` 46 处在用，且已与生产路径分叉（`wasTIFF` 语义、`plainText` 格式）。方向：把类型/优先级决策从 `extractRawData` 抽成纯函数 `CapturePolicy`，46 条断言迁到它上面，然后删旧路径。这是采集正确性的核心测试面，目前测的是用户不跑的代码。
- `isDatabaseCorrupted` 三处写入、零处读取，`recoverDatabase()` 只是 close + open。方向：与 §4.4 的 integrity_check 合并，否则删掉这个 flag。
- `MockClipboardService`（751 行）在 `Scopy/Services/` 随发布二进制一起打包；`Scopy/Views/UITesting/` 四个 harness 视图 1,063 行进 Release。方向：`#if DEBUG` 或独立 target。

### 8.5 并发模型（P1，M；与 §4.5 同一件事）

现状：`StorageService` `@MainActor` 但几乎全是 `try await repository.x` 一行转发（`:721-793`）；一次复制约 20 次 executor 跳转、至少 5 次落在主线程；`ClipboardService` 有 18 处 `MainActor.run`、62 处 `await storage./await search.`；`synchronizeSearchWithCurrentItem` 的 3 次重读循环（`:1972-1996`）防御的正是这些多余跳转制造的重入。六个手写 continuation 队列同构（`BoundedCoalescingWorkerQueue`、`ClipboardEventQueue`、`ClipboardItemMutationGate`、`AsyncBoundedQueue`、`ThumbnailDecodeCoordinator`、`ExternalFileReservationRegistry`）。`ClipboardMonitor.queueLock` 与 `StorageService.externalSizeCacheLock` 保护的是本已 actor 隔离的状态，只为 `deinit` 能碰。`ScrollCursorSetCoalescer` 在生产无条件 swizzle `NSCursor.set`。`ClipboardMonitor.testingAsyncProcessingDelayNs` 是 `nonisolated(unsafe) static var` 且生产 ingest worker 会读。

方向：先做 §4.5（`StorageService` 脱离主 actor），然后把六个队列收敛为一个泛型 waiter/generation 原语放进独立 `ScopyConcurrency` 目录；去掉双重隔离的锁（deinit 不再触碰隔离状态）；swizzle 保留但加环境变量关闭开关；测试旋钮走注入而非全局可变静态。`ClipboardService.swift` 1-633 行的四个通用原语与剪贴板无关，随之移出。

现有的 publication token / `isLatest` / mutation gate 协议是对的，不要动它们的语义，目标是让它们不再那么必要。

### 8.6 生命周期与内存压力（P1，S + M）

- 无 `NSWorkspace.willSleep/didWake`、无 `didChangeScreenParameters` 处理：500 ms 轮询定时器跨睡眠盲跑，唤醒后 `changeCount` 跳变无重新基线；面板位置不随显示器变化校验。S。

- `HoverPreviewImageCache` 单例的 15 s 清理循环永不取消。方向：有条目时才跑。S。
- 无单实例守卫：两个 Scopy 会同时读写同一个 DB。S。
- Sparkle 在 Scopy 自己的服务之前启动（`AppDelegate.swift:43-49`）。顺序调整。S。
