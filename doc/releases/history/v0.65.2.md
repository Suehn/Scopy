# v0.65.2

## Summary

`v0.65.2` makes dense search results explain themselves. Every candidate from a non-empty text search now shows compact, highlighted evidence for why it matched, including the source and additional-occurrence count when one item contains several matches. The release also removes the obsolete project-level Trellis workflow in favor of the repository's canonical guidance.

## Search Experience

1. Shows a keyword-in-context excerpt for every candidate instead of asking users to distinguish similar results from thumbnails and truncated titles alone.
2. Highlights only ranges that follow the active search mode's real matching semantics.
3. Labels evidence from clipboard content, notes, file paths, and image metadata.
4. Shows up to two excerpts when useful and reports the remaining occurrence count or lower bound without making rows unbounded.
5. Uses positional evidence for zero-width regular-expression matches and stable fallback text only when the matching source has no visible characters.
6. Preserves search sorting, filtering, pagination, selection, copying, thumbnail behavior, and non-search row layout.

## Correctness and Architecture

- Search results carry a typed match context from the backend to presentation instead of re-deriving evidence in SwiftUI.
- FTS evidence uses SQLite's own `unicode61` tokenizer, keeping highlighted token boundaries and diacritic behavior aligned with candidate selection.
- Exact, fuzzy, fuzzy-plus, regex, recent-cache, full-index, and staged-refinement paths share the same evidence contract.
- Evidence construction is included in the search timeout and metrics, prepares reusable matchers once per request, and cooperatively observes cancellation during long scans and regex enumeration.
- Query and mode transitions clear stale projections; delayed old searches and pages cannot restore obsolete rows, evidence, or loading state.
- Content updates re-run an active semantic search, while metadata-only updates preserve the current result order and evidence.

## Performance

The feature intentionally performs bounded work to explain returned candidates. A same-host, same-snapshot comparison against `v0.65.1` therefore records higher search latency rather than claiming a speedup:

- Service P95: `cm 4.490ms -> 9.449ms`, `数学 8.307ms -> 15.174ms`, and `cmd 0.124ms -> 0.927ms`.
- Full-index warm load: `188.216ms -> 187.971ms`.
- Peak RSS: `222.391MB -> 220.391MB`.
- Snapshot Release gate: `cmd 0.947952ms / 50ms` and `cm 9.274006ms / 20ms`.

The three-repeat full frontend profile waited for an active regex query before scrolling. All six baseline/current search runs loaded 550 rows with 550 evidence contexts. The current variant recorded search frame P95 `16.667ms`, row-body P95 `0.810ms`, and display-model P95 `1.736ms`. Frontend variants toggle existing runtime performance flags within the same candidate revision, so their deltas are regression observations, not a pre-feature causal comparison.
