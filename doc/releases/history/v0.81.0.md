# v0.81.0

## Summary

`v0.81.0` rebuilds the bundled `pngquant` from the fork's `perf2` branches. Dithering no longer spends time on flat areas that carry no error, the PNG writer compares the byte before and the rows above before searching, speed 1 dithers on all cores, and the previously unshipped phase 3/4 engine work is included. On the 2160×29511 reference page the tool runs 2.1× faster at the default export settings (`207 -> 99 ms`) and 5.4× faster at speed 1 with 16 colors (`861 -> 159 ms`). At speeds 2-10 the output decodes to the same pixels except where chunk borders moved on pages taller than 2,816 rows; speed 1 produces an equivalent dither pattern; file sizes stay within `-3.3%..+0.9%`. No Swift source changed.

## Why This Release

After `v0.75.0` the tool took about 0.2 s of a 0.8 s export at the default settings and 0.9 s at speed 1 / 16 colors. Profiling the reference page put dithering and deflate at about 0.8 s of CPU each, and two properties of document pages explain both:

- 92% of the pixels are exactly a palette color (background, text) and receive no dithering error, so the nearest-color search and the error diffusion change nothing for them, yet every pixel went through both.
- 95% of the scanline bytes are copies of the byte before or of the row above. Level-9 zlib finds the row above only after thousands of steps along hash chains full of background positions; limiting the chain to 1024 steps already cost 2.7% in size.

## Key Changes

### Engine (fork `perf2` `b664d56`)

- An undithered pixel that is exactly a palette color without a duplicate is written without search or diffusion, since its error is exactly zero; the following pixels of that color without incoming error are written as a run, and rows of one such color without incoming error are filled without converting their pixels. Error rows are cleared only when they may hold error. Output is byte-identical.
- The nearest palette color of undithered colors is cached per chunk, only when no other entry is as near (checked against the whole palette), so a cached answer is what every search returns. Output is byte-identical.
- Speed 1 dithers in parallel chunks of at least 256 rows that start with 16 rows of diffusion, instead of on one thread.
- Dithering uses 16 chunks per core instead of 8, which balances pages whose flat rows now cost almost nothing.
- Histogram counting adds runs of identical pixels at once (same counts).
- The discarded warm-up row is zeroed; warm-up rows read palette guesses from it, which was uninitialized memory before.
- Merged the 2026-09-05/06 phase 3/4 engine work, which had never shipped: NEON contrast maps, blur and median-cut weights, same-alpha color distances, a vector fast path for adding dithering error within the gamut, and per-thread dithering buffers. It was verified pixel-identical on 272 image/setting combinations in that work and is byte-identical here to the branch without it. Its experimental `palette-reuse` feature (256 colors at quality 0-100 only, changes the search) is not included.

### PNG writer (fork `perf2` `624df85`)

- `vendor/zlib-rs` is zlib-rs 0.6.7 with `set_match_hints`: candidates at given distances are compared before the hash chain. The writer passes the byte before and the row above.
- Images of at least 8 MiB of scanlines: 256 KiB pieces that are at least 90% copies of the byte before or the row above use level 8 with a 64-step chain and hints for four rows above; other pieces keep level 9 with half the chain (a quarter after an 8-byte match). Smaller images use level 9 with hints throughout, where the shorter search would save little time and could cost size. Output is still independent of the thread count.
- 8-bit rows are compressed where they are: `pngquant.c` lays out the indexed image as PNG scanlines, which removes a 64 MB copy on the reference page.
- Adler-32 is computed per piece in parallel and combined.

### Scopy

- `Scopy/Resources/Tools/pngquant` and `Scopy/Resources/ThirdParty/pngquant/PROVENANCE.md` only. Settings, defaults and `PngquantService` are unchanged. Rich v2 documents still keep true-color output without pngquant.

## Verification And Performance

Apple M3 Pro (5P+6E), macOS 15.7.3, rustc 1.98.0. Whole CLI runs with Scopy's arguments, the v0.80.7 binary against the v0.81.0 binary, interleaved, minimum (median) of 5-15 runs:

| Workload | v0.80.7 | v0.81.0 | Speed-up | Size |
| --- | ---: | ---: | ---: | ---: |
| Reference page 2160×29511 (PAM), speed 3, 256 colors, 80-95 (export default) | `207 (212) ms` | `99 (102) ms` | 2.09× | -0.07% |
| Same page, speed 1, 16 colors, 0-70 | `861 (864) ms` | `159 (160) ms` | 5.43× | +0.93% |
| `chatgpt_rich_surfaces` 2160×16813 (PAM), export default | `237 (249) ms` | `159 (161) ms` | 1.49× | +0.17% |
| Capture: 2560×1600 UI PNG, speed 3, 65-100, `--skip-if-larger` | `80 (82) ms` | `72 (74) ms` | 1.11× | -0.03% |

Stages of the default reference run: quantize `24 -> 22 ms`, remap `85 -> 36 ms`, write `87 -> 32 ms`; at speed 1, remap `744 -> 92 ms` and write `79 -> 32 ms`. The capture is bound by Cocoa's PNG decode (`27 ms`) and by quantizing a small image, which this release barely changes.

Deflate on the reference scanlines (63.8 MB, 8-bit): level 9 gives `2,858,630` bytes for `921 ms` of CPU; level 9 limited to 1024 chain steps +2.7%; level 8 with hints for the byte before and up to four rows above and a 128-step chain +0.03% at 2.8× less CPU. Rewriting rows with PNG's `Up` filter instead was tried and rejected (+3.9% to +24%).

In the app (Debug build of this commit against the installed v0.80.7 Release, UI-test auto-export at the code defaults): `preview-fixture.md` at 100% (1080×667) exports palette PNGs with identical pixels (`27,183 -> 27,182` bytes). `user_markdown_stress.md` at 200% (2160×137823, 298 megapixels, tiled) goes from `6.35-6.57 s` to `5.85-5.90 s` from launch to PNG, with 0.0006% of pixels at moved chunk borders and a 0.01% smaller file. The `chatgpt_public_copy` page renders as rich v2 and keeps its true-color output in both versions (byte-identical).

Quality and sizes:

- Speeds 2-10 decode to the same pixels on the bench set (four bench images and `test.png`; speeds 1/4/10, `--nofs`, `--posterize 2`, `--quality 60-80`; one and all threads). On pages taller than 2,816 rows the chunk borders move: reference page 0.05% of pixels, MSE `0.5111 -> 0.5109`, 3×3/7×7-blurred MSE `0.1377/0.0883 -> 0.1378/0.0884`; `chatgpt_rich_surfaces` 1.5% of pixels, MSE `2.3702 -> 2.3656`, blurred MSE +0.2%.
- Speed 1: reference page at 16 colors 0.14% of pixels, MSE `9.9593 -> 9.9599`, blurred MSE `4.9412/3.6221 -> 4.9417/3.6224`; bench images up to 3% of pixels, MSE within 0.1%.
- Sizes: bench set `-3.3%..+0.2%` (0.1% smaller in total); pages as in the table.
- One and all threads give byte-identical output (58/58). The x86_64 (Rosetta) and arm64 slices decode to identical pixels on the pages; 4 of 29 bench outputs differ in 0.0003-0.02% of pixels (floating-point paths) with the same MSE to four digits.
- Fork tests: engine 28 with and without `threads` (new: exact colors stay exact while dithering, cached answers match every search, gamut fast path, same-alpha search), CLI 4 (round trips of flat, noisy and wide-stride data through the writer).

## Current Status

Exports compress 2× faster at the defaults and more than 5× faster at speed 1. Pixels are unchanged apart from moved chunk borders on very tall pages at speeds 2-10 and an equivalent dither pattern at speed 1.

## Remaining / Next

- Captures are bound by Cocoa's PNG decode and by palette search on small images.
- On image-heavy pages the median-cut and k-means feedback loop now dominates quantization, and it runs on one or two cores by design.
- The fork's `perf2` branches are the corresponding source of this GPL binary and should be published.
