# v0.74.0

## Summary

`v0.74.0` removes the PNG round trip from Markdown/LaTeX export and replaces libpng's level-9 encoder in the bundled `pngquant` with a parallel zlib-rs writer. The rendered bitmap is handed to `pngquant` as raw RGBA pixels (a preallocated, memory-mapped PAM file that the tool maps directly), so neither Scopy's ImageIO PNG encode nor the tool's Cocoa PNG decode runs anymore, and the quantized PNG is compressed on all cores. On the 2160x29511 reference export the stage from finished bitmap to final PNG drops from about 2.55 s to about 0.34 s (7.5x), the whole export from app launch to the PNG on the pasteboard drops from 6.2 s to 3.6 s, and the output is pixel-identical to `v0.73.0` while 0.7% smaller. Quantization settings, defaults, and quality are unchanged.

## Why This Release

After `v0.73.0` the quantizer was a few percent of export time. Measured on the reference export, the rest was structural: Scopy encoded the bitmap to an RGBA PNG with ImageIO (403 ms), `pngquant` decoded it again through Cocoa (256 ms), quantized it (135 ms), and then spent 1.3-1.8 s in libpng's single-threaded level-9 deflate. The user's goal was a 5-10x faster export without visible quality loss, so both halves had to go: the encoder became a Rust writer that deflates fixed 256 KiB pieces in parallel (each primed with the preceding 32 KiB so the ratio matches a sequential stream, joined with sync flushes into one zlib stream, level 9 and memLevel 5 like libpng), and the decode disappeared by feeding the tool the pixels Scopy already holds.

## Key Changes

### Bundled pngquant (fork `perf` branch `256e081`)

- `rust/pngwrite.rs` replaces libpng for all output: scanlines are packed in parallel (1/2/4/8-bit palette rows use filter 0; the truecolor fallback keeps libpng's adaptive filter choice), deflated as dictionary-primed 256 KiB pieces with zlib-rs, and emitted with `crc32fast`/`simd-adler32`. Piece boundaries are fixed, so the bytes do not depend on the thread count. IDAT chunks are 256 KiB; `gAMA` now precedes `sRGB`.
- `rust/rwpng_cocoa.rs` accepts PAM (`P7`, 8-bit `RGB_ALPHA`) input and maps regular files with `mmap`, so the quantizer reads the caller's pixels with no decode and no copy; every other input still goes through Cocoa. `--verbose` prints per-stage timings.
- `--skip-if-larger` now decides before writing, so a too-large result writes nothing instead of a partial file; `build.rs` reruns on C source changes.
- Verified on palette, `tRNS`, 4-bit, and truecolor-fallback outputs: scanlines byte-identical to the libpng writer; file sizes `+0.09%` (reference export), `-0.58%`, `-0.24%`, `-0.40%`, `+0.47%` (fallback).

### Scopy

- `PngquantService` runs the tool in file mode only (`--output`, input path, stdin and stdout unused), which also stops the tool from re-encoding the 24-bit original on the no-change exits. `compressBitmap(_:options:)` writes the flattened bitmap into a preallocated (`F_PREALLOCATE`) and memory-mapped PAM file with a 64-byte-aligned header and returns `nil` when the tool declines (exit 99).
- `MarkdownExportService.encodeExportImage` feeds all three export paths (PDF raster, single snapshot, tiled) through the bitmap hand-off and falls back to ImageIO only when pngquant is disabled or declines; the encode stage and encoder are logged with their duration.
- `ExportStats` now carries `finalPNGBytes` and `pngquantApplied` instead of a saved percentage (there is no unquantized PNG to compare against anymore); the success toast reads `Exported PNG (2x, pngquant 1.9 MB)`.
- Exports no longer pass `--skip-if-larger` (a raw input has no reference size); the only way pngquant declines an export is the quality floor, and then ImageIO encodes the bitmap as before.

## Verification And Performance

Apple M3 Pro (5P+6E), macOS 15.7.3, rustc 1.98.0. Reference input: the `chatgpt_public_copy_markdown_sample.md` fixture exported at 200% (2160x29511, 63.7 Mpx, ImageIO PNG 7.8 MB), Scopy's arguments (`--quality 70-85 --speed 3 --strip 256`), min of 3 runs.

| Stage | v0.73.0 | v0.74.0 |
| --- | ---: | ---: |
| Scopy: bitmap to tool input | ImageIO PNG encode `403 ms` | PAM preallocate + map + flatten `110 ms` |
| Tool: input | Cocoa PNG decode `256 ms` | `mmap` `4 ms` |
| Tool: quantize + dithered remap | `135 ms` | `114 ms` |
| Tool: PNG write | libpng + zlib level 9 `1.3-1.8 s` | parallel zlib-rs level 9 `93 ms` |
| Whole tool | `2.05 s` | `0.21 s` (PNG input: `0.56 s`) |
| Export stage (bitmap to final PNG) | about `2.55 s` | about `0.34 s` |
| App launch to PNG on pasteboard | `6.10-6.32 s` | `3.50-3.70 s` |

Encoder choice on the reference scanline stream (31.4 MB, single thread unless noted): system zlib level 9 memLevel 5 `1777 ms`; zlib-rs level 9 `497 ms`; libdeflate level 9 `224 ms` but 2.3% larger; zlib-rs level 9 parallel 256 KiB primed pieces `76 ms` (11 threads) at the same size as the sequential stream. memLevel 5 compresses palette scanlines 1.6% better than the default 8, which is why the writer keeps libpng's setting.

Correctness: the export produced by the old and new app builds from the same fixture has identical palette and scanlines (`1,973,376 -> 1,959,158` bytes); the tool's PNG and PAM inputs give identical scanlines; `x86_64` and `arm64` slices give identical files on the bench set and differ in 0.002% of index bytes on the 63 Mpx export, as the previous build already did.

## Current Status

Exports and image compression use the same settings as before; only the transport between Scopy and the tool and the tool's PNG writer changed. Captured images (already PNG files) keep the PNG input path and gain the faster writer.

## Remaining / Next

- The export stage is now bounded by the dithered remap (about 90 ms) and the parallel deflate (about 90 ms) on a 63 Mpx page; overlapping the two would be the next step if more is needed.
- The remaining end-to-end time is app launch plus WebKit layout, PDF export, and rasterization, outside the encode/decode path.
- The fork's `perf` branches are the corresponding source for the GPL binary and should be published alongside the release.
