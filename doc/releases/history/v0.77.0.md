# v0.77.0

## Summary

`v0.77.0` finishes the history-list scroll work that `v0.76.0` started, under one constraint: nothing the user sees changes. Three findings drove it. With a mouse wheel the app never knew it was scrolling (legacy wheel events post no live-scroll notifications), so every row passing under the pointer opened a hover session and, for images, started a full-resolution preview decode; a selection change re-ran the whole `List` body, which re-initializes every ForEach child and diffs every loaded id; and a 500-row page load did that for 500 fresh rows at once, each paying a descriptor miss. Fixing those takes mouse-wheel scrolling from `9.9 s` to `2.9 s` of CPU per 12 s, halves main-thread busy time again (42% -> 22%), holds callback-interval p95 at one 120 Hz frame (8.3 ms), and removes the 75 ms page-load hitch. Against `v0.75.0`, where this work began, scroll CPU is 5x lower and callback p95 10x lower.

## Why This Release

A floor experiment (`logs/perf-scroll/floor-experiment/`, minimal lists driven by the same real wheel input) bounded what was possible: a plain-text SwiftUI `List` costs `1.3 s`, an `NSTableView` with AppKit cells `0.66 s`, and Scopy with a stripped-down row `3.4 s`. The goal agreed with the maintainer was `2.5-3.0 s` total, `18-22%` main thread, p95 `8.3 ms` with the experience unchanged; the maintainer asked to ship before the remaining test tiers finish.

## Key Changes

- `ListLiveScrollObserverView` reports one unified scrolling state: live-scroll notifications (trackpad) and the list clip view's `boundsDidChange` (mouse wheel, momentum tail) both start it, and it ends only after the gesture finished and the clip view has been still for 120 ms. Mouse-wheel scrolling therefore suppresses hover sessions, preview decodes, thumbnail priority, and the relative-time clock exactly as trackpad scrolling already did. `ListProgrammaticScrollGate` masks the keyboard-selection `scrollTo` so it does not retire the hovered row.
- `HistoryRowSelectionFanout`: `HistoryViewModel.selectedID.didSet` fans the change out to the two rows it concerns. Each ForEach child is a `HistorySelectionAwareRow` holding its selection as local state; `HistoryListView.body` no longer reads `selectedID`, and keyboard follow hangs off the fan-out callback.
- `loadMorePageSize` 500 -> 100 (the documented page size); `HistoryItemView` resolves its row descriptor lazily from `HistoryItemPresentationCache` instead of in `init`; `ClipboardItemDisplayText.prewarm` uses memoized revisions.
- `ListLiveScrollObserverView.layout()` resolves the scroll view only until attached; `PerfFeatureFlags.passiveHistoryRowEnabled` is read once.
- Profiling: `scripts/perf-scroll/profile_scroll.py --phased` sends trackpad-like gesture phases, `--reuse-db` measures steady state on a warmed database copy.

Measured and reverted, recorded in `doc/current/development-guide.md` so they are not retried: a list-level tracking area replacing per-row `.onHover` (no gain: the pointer-region cost belongs to `NSHostingView` cell reinsertion), and merging the row's background/overlay/animation modifiers (no gain once hover churn is gone).

## Current Status

Hover highlight, hover previews, context menus, popovers, keyboard navigation, and selection look and behave as before. The one visible difference is a fix: with a mouse wheel, hover previews no longer start while the list is still moving, which is what trackpad scrolling already did.

## Remaining / Next

- The remaining main-thread cost is SwiftUI `List` machinery: CA commit and hosting-view layout (~14%), AttributeGraph (~11%), `NSTableView` recycling (~8%), automatic row heights (~5%). Going below the ~2.6 s floor of this design needs `NSTableView` with AppKit cells (floor 0.66 s), which cannot promise an identical experience.
- Every `List` body run still initializes every ForEach child; anything else that changes per interaction should reach rows the way selection now does.
- The panel costs ~8-10% GPU while idle (blur material suspected, not verified); unrelated to scrolling.
