# v0.85.0

## Summary

This release gives capture, history requests, previews and cached media clearer ownership, removes repeated search and renderer work, and adopts Swift 6. The existing interface, settings transaction, clipboard semantics and macOS 14 support remain the product contract.

## Changes

- Capture reuses each pasteboard representation once. Shutdown waits for accepted capture, storage and publication work before closing the database and releasing its writer lock.
- History requests, row subscriptions, relative-time updates and hotkey recording have explicit owners. Closing Settings releases its draft and input handlers; Save/Cancel and existing keyboard behavior are preserved.
- Hover preparation, pinned previews, export and thumbnail loading retain their resources until the owned work finishes. Pending pinned windows can be invalidated before they appear, and old callbacks cannot close a replacement.
- Search shares one UTF-8 traversal helper and reduces repeated scans and temporary allocations. SQLite cancellation follows the task executing the query.
- Markdown tables prepare their structure once and finalize column sizes after images settle; scientific-source placeholders restore in one pass. Preview and PNG still use the same renderer and document.
- Development, tests and releases use Xcode 26.1.1 and Swift 6, with a macOS 14 deployment target.

### Behavior fixes

- EXIF-rotated hover images decode to the displayed width.
- Invalidated thumbnail work cannot repopulate the cache or release its concurrency slot before decoding ends.
- Orphan cleanup uses the same path reservations as payload placement, without discarding a sweep after an unrelated database write.

## Release Performance Comparison

Measurements used an Apple M3 Pro with 36 GiB RAM on AC power, macOS 15.7.3 and Xcode 26.1.1. The baseline is v0.84.0; both variants used isolated copies of the same 10,000-row snapshot (20.9 MB of UTF-8 text, database SHA-256 `bfcf282096b49a1f5df2c88f906ddb53dff1b66ec1d4972e68cb53337e2d38fe`). Each workload ran one warm-up per variant, three A/A pairs and three A–B–B–A groups, with Scopy, compilers and other benchmarks stopped. The source snapshot was unchanged afterward. The OS file cache may have been warm.

| Workload | v0.84.0 | v0.85.0 candidate | Interpretation |
| --- | ---: | ---: | --- |
| Full-index build phase, median | 1,560 ms | 892 ms | 42.8% lower; every candidate sample was faster than every baseline sample |
| Warm fuzzy+ `这个问题`, mean of run medians | 25.187 ms | 21.972 ms | 12.8% lower; every candidate run median was lower |
| Disk-cache warm load, mean | 40.68 ms | 41.41 ms | Within measured noise |
| Benchmark peak RSS, median | 103.75 MiB | 103.36 MiB | Within measured noise; not an application footprint measurement |

All samples were retained, including one 3.67-second baseline build and a 49.7-ms candidate query p95. The cold-build row uses medians so the outlier does not inflate the claimed improvement. These results do not establish improved tail latency or a whole-application speedup.
