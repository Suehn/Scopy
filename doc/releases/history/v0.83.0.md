# v0.83.0

## Summary

- Search short queries up to 8x faster, rebuild only changed history rows, keep deep search pages through new copies, and start over after a stale reopen

## Key Changes

- **Search, recent order:** one- and two-character queries and full-index fuzzy rankings score rows newest first and stop once the page is in, finishing the rows used at the same time. The next page continues where the previous one stopped. While such a scan is unfinished the total is unknown and the footer shows "N+ results".
- **Search, relevance order:** short queries decide most rows from the first 4 KB of their text and reuse their scores for later pages of the same query. The byte matcher validates and counts plain UTF-8 16 bytes at a time.
- **Match evidence:** snippet and highlight building is linear in the text: tokenization runs once over the UTF-8, and ranges come from byte counts. Output is unchanged (a differential fuzz of about 1.15 million cases found no difference).
- **Fuzzy+ refine:** ASCII words of three or more characters are narrowed through the short index's bigram postings.
- **Index caches:** a CRC-32 sidecar replaces SHA-256. Cache versions changed, so both caches are rebuilt once in the background on the first launch after the upgrade. A full-index build takes about 4.5 s on a 16,700-row snapshot in the benchmark; the in-app first launch was not timed.
- **History list:** a list update rebuilds only the rows whose inputs changed. A capture, edit or deletion during a deep search or filter list keeps the loaded rows instead of collapsing them to the first page. The hover WebView is built once per list, and a bulk deletion updates search evidence once instead of once per row.
- **Stale reopen:** a hotkey open more than 3 minutes after the panel closed starts over, with or without a query: the query and selection are cleared, and the list is back to its first page and scrolled to the top. A hotkey open within 3 minutes and an open from the status item keep the query, the loaded rows and the scroll position.
- **Fixes:** pinned previews no longer close on every capture once 4,096 deletions have been recorded; the first history load finishes while events keep arriving; a repeated search hit is shown once instead of crashing the list.
- **Development:** the scroll profiler's start barrier keeps the measurement window closed until it is released; the snapshot gate's prepared `cm` run searches another query first so it still times a fresh ranking; perf scripts copy every database file of a snapshot. Native tests went from 742 to 760.

## Performance

- Release ScopyBench, `v0.82.2` (`c05ba8d`) against this release's search code, on a 16,771-row real snapshot, each binary on its own APFS clone, 5 interleaved A-B-B-A groups after 3 A/A pairs. Means of run medians; every candidate run beat every baseline run.

| Workload | v0.82.2 | v0.83.0 | A/A spread |
| --- | --- | --- | --- |
| Recent `e` (service) | 24.3 ms | 3.0 ms | 0.16 ms |
| Recent `co` (service) | 24.9 ms | 3.4 ms | 0.11 ms |
| Exact `的 是`, 300 rows (engine) | 446 ms | 171 ms | 2.5 ms |
| Prepared `cm` by relevance (engine, gate workload) | 15.4 ms | 7.4 ms | 0.11 ms |
| `cmd` by relevance (service) | 15.4 ms | 10.7 ms | 0.04 ms |
| Cold `cm` by relevance (service, first search) | 83.9 ms | 61.9 ms | 3.1 ms |

- Paging, measured per change because `v0.82.2`'s ScopyBench cannot time consecutive pages: ten 300-row pages of `e` by recency 419 → 134 ms; by relevance 263 → 122 ms.
- History list (Release app, isolated identity, interleaved): with 3,380 rows loaded, a capture costs 32% less main-thread time and 35% less CPU. With the panel closed after a deep scroll, ten captures cost 0.17–0.19 s of CPU after a stale reopen against 0.68–0.70 s without it, and the footprint is 154–158 MB against 181–195 MB.

- Each change's own A/B, differential fuzz and negative controls are in the release runbook sections dated 2026-10-18 (search stages 1–6) and in [history-list-depth-baseline-2026-10-18.md](../../perf/studies/history-list-depth-baseline-2026-10-18.md). No separate performance profile.
- Stale reopen on the local UI path (Release, isolated bundle identity, real hotkey path): 980 rows scrolled to rows 897–909 came back as 80 rows at the top; a "the" search scrolled to the bottom of 891 results came back with an empty query, 80 rows, at the top; a 5 s reopen kept 980 rows at rows 897–909.

Match-evidence equivalence was fuzzed on macOS 27.2 only; a release whose `Range(_:in:)` rounded an unaligned bound would shift that fragment's highlights.

## Installation

After the release is published, run `brew update` and `brew upgrade --cask Suehn/scopy/scopy`. New users can run `brew install --cask Suehn/scopy/scopy`.
