# v0.75.0

## Summary

`v0.75.0` makes Markdown/LaTeX export wait for layout by watching animation frames instead of sleeping, and makes the export canvas itself the raw PAM file that `pngquant` maps, so the bitmap is drawn exactly once. On the reference exports the work Scopy does after the page has loaded (measure, scale, capture, encode, hand over) drops from 1.4-2.8 s to 0.4-0.7 s, and from 13.6 s to 8.1 s on the 298-megapixel tiled stress page, while every output stays byte-identical to `v0.74.0` except for one row of the 63-megapixel snapshot export (206 pixels, 0.0003%, from Core Graphics' own banding of a single huge draw). Export defaults move to speed 3, 256 colors, quality 80-95.

## Why This Release

After `v0.74.0` the export timeline was dominated by fixed waits: layout was declared stable only after the measured height had not changed for 0.45 s, wide-content adjustment waited another 0.2 s plus 120 ms, and every scroll, resize, and scale change slept 70-80 ms regardless of whether WebKit had already finished. That floor was about 1.3 s per export, independent of page size. The pixel side still copied the bitmap three times on the snapshot path (upscale, flatten, hand-off). The user's goal was to bring the post-render part of an export under one second without visible change.

## Key Changes

### Frame-driven layout settle

- The export page now installs a small animation-frame watcher (`layoutWatcherJS`) that measures the export height every frame and counts consecutive unchanged frames. Swift polls it every 8 ms and treats layout as settled when at least two frames have run since the last change and the height has been unchanged for three frames, with render readiness (fonts, images, stylesheet, paint) still required from the page's own `__scopyIsRenderReady`. If frames stop (occluded view) it falls back to 0.45 s of unchanged height.
- The same watcher replaces the fixed sleeps after `applyGlobalScale`, `scrollTo`, and `resizeWebViewForSnapshot`, and the multi-pass `reconcileExportHeightPoints`; wide-content adjustment retries at most three times instead of until the 12 s deadline.

### The canvas is the PAM file

- `ExportBitmapCanvas` is always backed by a preallocated, memory-mapped PAM (`P7`, 8-bit `RGB_ALPHA`) file with a fixed 128-byte header. The PDF raster, single-snapshot, and tiled paths draw straight into it; the header is rewritten and the file truncated after the blank-row trim; `pngquant` then maps that file. `PngquantService.compressPAMFile(_:options:)` replaces the bitmap hand-off, and ImageIO encodes from the same mapping only when pngquant is disabled or declines.
- The single-snapshot path draws the snapshot scaled onto the white canvas in one pass, in 256-row bands on all cores, instead of upscale + flatten + copy.
- The blank-row trim keeps its existing behaviour exactly (it scans from the top of the buffer and drops rows beyond a 40-pixel margin), now as an in-place move instead of a crop.

### Defaults

- `SettingsDTO.default` export compression is speed 3, 256 colors, quality 80-95 (was 70-85). Saved user settings are unchanged; the higher floor means pngquant declines more photo-like pages, which then export losslessly through ImageIO.
- UI-test auto-export accepts `SCOPY_UITEST_PNGQUANT_EXPORT_DEFAULTS=1` to run with the code defaults regardless of saved settings; export stage transitions are logged.

## Verification And Performance

Apple M3 Pro, macOS 15.7.3, Debug build driven through the UI-test auto-export hook; times are from app launch, and "post-load" is from the `prepareLayout` stage (page loaded) to the PNG being written. Fixture exports use the maintainer's saved settings (speed 1, 16 colors, quality 0-70) so outputs can be compared byte for byte with `v0.74.0`.

| Fixture | Path | v0.74.0 total | v0.75.0 total | Output |
| --- | --- | ---: | ---: | --- |
| chatgpt_public_copy 200% (2160x29511) | snapshot | `3.57 s` | `2.05 s` | identical |
| chatgpt_public_copy 100% (1080x14769) | snapshot | `2.55 s` | `1.40 s` | identical |
| rich_markdown 200% (2160x8983) | PDF | `2.27 s` | `1.14 s` | identical |
| chatgpt_rich_surfaces 200% (2160x16813) | PDF | `3.07 s` | `2.02 s` | identical |
| user_markdown_stress 200% (2160x138038) | tiled | `14.24 s` | `8.73 s` | identical |

Stage detail on the 200% reference page: `prepareLayout` `1.15 -> 0.14 s`, `applyScale` `0.15 -> 0.07 s`, `snapshotOnce` `0.22 -> 0.14 s`, snapshot-to-canvas draw `0.31 -> 0.07 s` (banded); the remaining time is the tool at speed 1.

With the new defaults (speed 3, 256 colors, 80-95), post-load time: chatgpt_public_copy 200% `0.79 s` (total `1.51 s`), chatgpt_public_copy 100% `0.65 s`, rich_markdown 200% `0.45 s`, chatgpt_rich_surfaces 200% `0.86 s`.

Banded drawing versus a single full-canvas draw on the 63-megapixel snapshot: 206 of 63,743,760 pixels differ, all in one row, maximum channel difference 27; the same 206 pixels differ for 256-row and 1024-row bands with or without overlap, so the difference is intrinsic to Core Graphics' single large draw, not a seam.

## Current Status

Exports produce the same pixels as before at the same settings, sooner. The bundled `pngquant` is unchanged from `v0.74.0`.

## Remaining / Next

- Pages above the 60-megapixel PDF budget are still captured at the display's backing scale (1632 px for an 816 pt view) and upscaled to the requested width; capturing at the target width through the existing transform scale would remove that resample and sharpen those exports.
- The tiled path scales each tile separately before stitching; drawing tiles straight into the canvas would remove one resample per tile.
- The blank-row trim scans from the top of the image although its comment describes trimming the bottom; behaviour was preserved unchanged and should be decided on separately.
