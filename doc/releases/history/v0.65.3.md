# v0.65.3

## Summary

`v0.65.3` is a performance-only release: it makes the search-index disk cache survive app restarts, keeps the interactive full-index warm-up build alive while the user types, turns the after-write corpus-metrics aggregate into an index-only scan, and removes the main-thread deep array comparison from the history list. Search results, ranking, UI behavior, and interaction are unchanged; every fix removes waste on an existing path.

## Performance Fixes

1. **Disk-cache invalidation by logical content, not file attributes.** The full-index and short-query disk caches previously fingerprinted the database by file size/mtime of the DB/WAL/SHM files, so the quit-time WAL checkpoint invalidated them on every restart and cold start always rebuilt from a full table scan. Caches are now stamped with `scopy_meta.mutation_seq` (plus a live item-count tripwire) and stay valid across restarts as long as the logical content is unchanged. Cache formats bumped to `fullindex.v4` / `shortindex.v2`; stale older cache files are removed at engine open.
2. **Warm-up builds survive typing.** The interactive full-index warm-up session was keyed by the lowered query string, so every keystroke cancelled and restarted the background build and heavy corpora repeatedly paid full-table scans without ever finishing. The trigger no longer carries a query payload; one shared warm-up session stays alive for any interactive fuzzy request and ends only when the user leaves the fuzzy-search context.
3. **Corpus metrics via expression index.** The first search after every clipboard write ran `COUNT(*) + AVG + MAX(LENGTH(CAST(plain_text AS BLOB)))` as a full table scan over all text payloads. Schema v9 adds the expression index `idx_plain_text_bytes`, which serves the unchanged aggregate query as an index-only scan.
4. **History list observes a revision token instead of the items array.** `HistoryListState` now maintains `itemsRevision`, bumped on every items mutation, and `HistoryListView` observes it instead of `items`, eliminating the O(loaded plain-text bytes) element-wise array comparison on the main thread.

## Correctness and Architecture

- The persist path stamps caches with the engine's `knownDBChangeToken` — the mutation sequence its in-memory index content actually corresponds to — instead of re-reading files or the DB at persist time, removing the old fingerprint's time-of-check/time-of-use race.
- Databases without `scopy_meta` simply do not participate in disk caching; the legacy file-attribute fingerprint path is removed rather than kept as a fallback.
- `FullIndexBuildTrigger.interactive` carries no payload, so per-query cancellation is impossible at the type level.
- The expression index and the corpus-metrics aggregate share one byte-identical expression, verified by an `EXPLAIN QUERY PLAN` index-only scan.
- New regression coverage: `testFileChurnWithoutMutationDoesNotInvalidateFullIndexDiskCache` (WAL checkpoint plus file-attribute drift must not invalidate a logically unchanged cache — the production cold-start bug) and `FullIndexWarmupContinuityTests` (consecutive different queries must reuse one in-flight warm-up build). The obsolete SHM-drift fingerprint test was replaced, and the migration test now asserts the terminal `user_version` from `SQLiteMigrations.currentUserVersion`.

## Performance

Measured on the maintainer host (Apple M3 Pro, macOS 15.7.3, Xcode 26.1.1) against a same-day 9,566-item, 146 MB real snapshot; the real-database regression ran against an isolated copy of the live database (9,559 items):

- Cold-start deep fuzzy refine with a valid disk cache: `1789.7ms` (rebuild) → `271.6ms` (cache hit), identical result ordering (`testFullIndexDiskCacheLoadsAndMatchesRebuild`).
- Refine after typing with the warm-up build kept alive: `32.3ms`, versus `1903.2ms` for the cold no-prewarm sync path (`testColdStartPrefilterWarmsFullIndexAndRefineMatchesOnDemandResults`).
- Corpus-metrics aggregate on the real database: `268ms` full scan → `<1ms` index-only scan (~500×), paid on the first search after every clipboard write.
- Snapshot Release gate: `cmd p95 0.612ms` against `50ms`, `cm p95 5.352ms` against `20ms`.
- Same-host, same-snapshot backend audit vs `v0.65.2`: service P95 `cm 5.237ms -> 5.246ms`, `数学 24.801ms -> 24.379ms`, `cmd 0.565ms -> 0.634ms`, `cm:noThumb 5.375ms -> 4.763ms`; peak RSS `191.03MB -> 155.03MB`. Engine-level `cm` rows moved in the audit run (`6.094ms -> 8.244ms`, forceFullFuzzy `7.402ms -> 12.109ms`) but an immediate re-run measured `5.100ms` / `5.209ms`, below baseline; the movement is run-to-run variance, and the re-run additionally benefited from the now-valid disk cache.
- Full-index warm load (cold build from DB): `234.7ms -> 254.0ms`, within run-to-run variance; the release's claim is cache validity across restarts, not a faster cold build.
- Full frontend profile (three repeats of 10 seconds, real snapshot): frame p95 flat at `0.00%` in mixed, search-evidence, and text-bias; the accessibility scenario moved one 8.333ms frame bucket (`33.333ms -> 41.667ms`) with long-frame attribution dominated by `19.2s` of cold thumbnail decodes in that variant, outside this release's paths. SwiftUI row-body p95 decreased in all four scenarios (`-7.8%`, `-2.2%`, `-2.0%`, `-0.6%`). Baseline/current compare runtime feature-flag variants within one revision and are regression observations, not causal claims.
- Unified backend/frontend table: `logs/perf-unified-2026-08-22_02-50-57.md`.
