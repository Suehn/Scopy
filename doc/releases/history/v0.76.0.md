# v0.76.0

## Summary

`v0.76.0` is the first history-list scroll release measured with real scroll-wheel input, the real panel, the real snapshot database, and a main-thread call-tree sample instead of the callback-interval harness. That measurement showed the cost was not in row rendering: 23% of the main thread went to AppKit re-setting the already-current cursor on every scroll frame (3 ms each under an Accessibility pointer customization), 11% to recomputing the content-revision cache key per row rebuild, and 9% to SwiftUI observation installed per row. Fixing those three cuts scroll CPU by a third, main-thread busy time in half, and callback-interval p95 from 83 ms to 17 ms with zero over-threshold callbacks, while GPU utilization halves.

## Why This Release

Past scroll work (v0.43.2 through v0.65.0) optimized row buckets that v0.7.4 had already measured at 2-3% of long-frame time, and the harness that judged it reports `TimelineView` callback intervals quantized to 8.33 ms steps, with the two largest shipped optimizations forced on in both A/B variants and XCUI drags standing in for scroll input. The maintainer asked for the actual bottleneck. `scripts/perf-scroll/` now drives the real panel with `CGEvent` scroll-wheel input (or the deterministic display-link workload), records CPU, GPU, and the app's own report, and attributes the main thread with `sample`.

## Key Changes

- `ScrollCursorSetCoalescer` swaps `-[NSCursor set]` and drops a set of the cursor that is already current when the same cursor was set less than 100 ms earlier. During scrolling AppKit's tracking-area manager and SwiftUI's `cursorUpdate` set the arrow cursor every frame; traced at about 70 calls per second, all redundant.
- `ClipboardItemContentRevision.resolve(item:)` memoizes the revision per item (validated against every input field) and encodes the digest without `String(format:)`; the row view, presentation cache, and view model use it.
- `HistoryListView` reads `selectedID`, `settings`, `activePopover`, and the search-match dictionary once per list update and passes them into the row builder, so ForEach children no longer install per-row observation.
- `SCOPY_PROFILE_OPEN_PANEL=1` opens the real panel at launch for profiling harnesses; `make perf-scroll-tools` / `make perf-scroll-wheel` build and run the new tooling.

## Current Status

Scrolling behaviour, hover, previews, selection, and context menus are unchanged; the list does the same work with fewer redundant system calls and rebuilds.

## Remaining / Next

- Per-row `.onHover` regions still cost about 6% of the main thread (`PointerRegionUpdater`) and keep tracking areas moving every frame; a single list-level hover tracker would remove both.
- SwiftUI List cell layout (`NSHostingView.layout`) and `NSTableView` row recycling are the largest remaining per-frame costs; they bound what row-level code can gain.
- The profiling driver's own display-link work is 12% of the fixed-workload sample; prefer the wheel workload for attribution.
- Users with the default pointer pay a much smaller version of the cursor cost; the coalescer is still correct for them.
