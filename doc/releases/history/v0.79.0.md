# v0.79.0

## Summary

`v0.79.0` is the third performance round. It removes two structural costs found by measuring the interactions with real input rather than by reading code: every list update was paying render work for every loaded row, and every clipboard write was copying the whole in-memory search index. Nothing a user sees changes.

## Why This Release

A full sweep of the interactive paths (panel open, activation, launch, keyboard navigation, delete, hover, typing) measured each one with posted `CGEvent` input against the real snapshot database. Most paths turned out to be healthy: the panel appears about as fast as the event system can deliver the hotkey, a row click puts content on the pasteboard in 7-9 ms, launch settles at 1.43 s of CPU, and idle costs about 0.04% of a core. Two costs stood out, and this release fixes the one with a contained, principled fix plus the index copy it uncovered.

## Key Changes

- Row construction (`HistoryItemView`): building the search-evidence attributed string, its accessibility description and the row-descriptor lookup moved out of `init` into a computed property used by the row's body. SwiftUI re-initializes every `ForEach` child on every list update, so with a search active the previous code paid all three for every loaded row on every keystroke, while a row's body only runs when the row actually changed. Row `init` is now assignment plus the memoized content revision.
- Search index mutation (`SearchEngineImpl`): the five upsert, pin and delete sites released the stored `fullIndex` / `shortQueryIndex` reference before mutating their local copy. Previously the property still referenced the same storage, so every clipboard write copy-on-wrote the buffers behind a 14.7 MB short index and a 24.7 MB full index instead of mutating them in place.
- Tooling (`scripts/perf-scroll/`): `panelwatch` (hotkey to panel-visible at ~0.4 ms resolution), `panelready`, `hoverstall` (main-thread stall meter built on Accessibility round-trip latency), `enterlatency` (activation to pasteboard to panel hidden) and `profile_interaction.py`. `profile_scroll.py` had a use-before-definition error that made it fail on every invocation, and it copied the superseded v4 plist index cache instead of the v5 binary caches, so every run rebuilt the index.

## Verification And Performance

Release builds, real 9,566-row snapshot database (warm copy), posted `CGEvent` input, main-thread blocking measured by Accessibility round-trip latency.

| Interaction | Before | After |
| --- | ---: | ---: |
| Search typing, 8 keys: main thread blocked | `291 ms` (mean of 4 paired runs) | `202 ms` (-31%) |
| Search typing: worst stall per run | `105 ms` (mean of 4) | `68 ms` (-35%) |
| Search typing: row descriptor lookups | `166` miss / `1245` hit | `75` miss / `699` hit |
| Search typing: `row.display_model` total | `110.3 ms` | `55.8 ms` |
| Search typing: `text.metadata` total | `108.9 ms` | `54.9 ms` |
| Clipboard capture, 12 text writes: process CPU | `0.372 s` (mean of 5 paired runs) | `0.328 s` (-12%) |

Regression checks:

- Mouse-wheel scrolling, 12 s, warm snapshot (4 baseline vs 3 candidate runs): CPU `3.82 -> 3.91 s`, main run-loop busy `2946 -> 2980 ms`, callback p95 unchanged. Both deltas are inside the `+-4%` run-to-run spread of the baseline itself, so this is recorded as no regression rather than as a change.
- Search results identical on the snapshot DB: `markdown` 42 hits, `状态` 49 plus 1 pinned, `cm` 50, and 42 again after inserting new items through the mutated index path. Rendered evidence text is byte-identical.
- `make test-snapshot-perf-release`: `cmd` p95 `0.526 ms` against a `50 ms` limit, prepared `cm` p95 `4.422 ms` against a `20 ms` limit, cold `cm` `59.510 ms` recorded only. All three are slightly better than the `v0.78.2` record.

## Current Status

Typing in the search field, scrolling, hovering, copying and capture behave exactly as before. The measurable difference is that a search keystroke blocks the main thread for about a third less time with shorter worst-case stalls, and each clipboard write costs about an eighth less CPU.

## Remaining / Next

- Presenting a hover preview still blocks the main thread `65-156 ms`; the cost is `NSHostingView.updateWindowContentSizeExtremaIfNecessary()` driving a synchronous `_NSPopoverWindow setFrame:` and a full view-tree layout. Fixing it means sizing the preview before presentation, which touches the Markdown preview contract and was left for its own round.
- After this change only about `12 ms` of the roughly `50-100 ms` cost of a list update is application code; the rest is SwiftUI's `ForEach` diff, NSTableView automatic row heights and Auto Layout. Publishing one page per keystroke instead of prefilter plus refine would cut list rebuilds from `1.5` to `1.0` per key, but it needs a deadline race inside the search state machine and was judged higher risk than its payoff.
- Copies made inside one 500 ms poll window are still lost rather than coalesced. The pasteboard does not retain contents the app did not read, so only a shorter poll interval narrows the window.
- `phys_footprint` still roughly doubles (93 -> 192 MB) after the first search of a session and stays there; the in-memory fuzzy index is never released.
