# v0.78.0

## Summary

`v0.78.0` is the second performance round after the scroll work, aimed at the interactions a user feels most: hovering a row, typing a search, copying something, launching the app, and scrolling into the next page of history. Each change was measured with real input on the real panel and the real snapshot database first, and nothing the user sees changes except that things happen sooner.

## Why This Release

A code review across the capture, preview, search, startup and idle paths ranked the remaining costs by user impact (see the runbook section for this release). The maintainer chose to do all of them, with one balance point: preview work may start only after the pointer has rested on a row for 300 ms, so passing over rows costs nothing.

## Key Changes

- Hover preview (`HistoryHoverPreviewPipeline`, `MarkdownPreviewWebViewController`, `MarkdownPreviewLayoutScalePreference`): after 300 ms of hovering, Markdown detection, render context and HTML build run off the main actor; the shared WebView loads the document offscreen at the popover width and the page's layout probe seeds the metrics cache, so at the preview delay the popover opens at its final size with the render already on screen, and a warm hover navigates nothing. The pipeline renders at the scale the popover shows; previously a preview-local scale different from Settings rendered every hover twice. Image and file previews prefetch at the same 300 ms.
- Search typing (`HistoryViewModel`, `HistoryListView`): the current rows stay until the versioned replacement arrives (no empty flash per keystroke), a refine pass identical to the prefilter page is skipped, and `isLoading`, `performanceSummary` and the workload observers moved out of the List body into leaf views so they no longer rebuild every row.
- List state (`HistoryListState`): front inserts, in-place replacements and page appends update the derived arrays incrementally instead of rebuilding them.
- Clipboard capture (`ClipboardMonitor`): text representations are processed off the main thread; the WebKit HTML importer, which must run on the main thread, is invoked only when it can change the stored text. Stored text and hashes are unchanged.
- Search index caches (`SearchIndexBinaryCodec`): the short and full index caches use a compact binary encoding whose header rejects stale caches before checksum or decode.
- Page loads: the next page is requested 40 rows before the end and applied in 20-row chunks one display frame apart.
- Preview image cache: entries up to 256 MB under a 320 MB total, so a tall screenshot's preview stays cached instead of being decoded on every hover; decode quality is unchanged.
- Tooling: `scripts/perf-scroll/profile_search.py` (real key events into the search field) and `profile_capture.py` (writes to the app's private pasteboard: text, rich, RTF-only, HTML-only, image), plus `pbwrite`, `typekeys`, `click`, `axsearch`, `axrows`; hover and capture stage timelines in the app's info logs.

## Verification And Performance

See `doc/perf/release-profiles/v0.78.0-profile.md`.

| Interaction | Before | After |
| --- | ---: | ---: |
| Markdown hover, cold: final content on screen | `1.33 s`, two navigations, two resizes | `1.04 s`, one offscreen navigation, final size on first frame |
| Markdown hover, warm | `1.31 s`, two navigations | `1.04 s`, no navigation |
| Search typing, 14 keys: List body runs / rows re-initialized | `56 / 541`, list emptied per key | `31 / 486`, rows kept |
| 1 MB rich copy: main thread blocked | `1.9-2.4 s` per copy (58.5% of samples) | `~0` (0.3% of samples) |
| Launch: short-index cache load | `2,887 ms` (stale plist decoded, then rejected) | `0 ms` stale / `55 ms` hit |
| Launch CPU, first 12 s | `3.3 s` | `0.75 s` |
| Page load while scrolling: longest callbacks | `25-33 ms` bursts | `17 ms` (two frames) |

Gates on the release candidate:

- `make test-unit`: 791 executed, 3 skipped, 0 failures on the release source.
- `make docs-validate`, `make release-validate`, `make test-release-policy`: passed.
- `make test-strict` and the UI subset (`HistoryListUITests`, `HistoryListRetainedInteractionUITests`, `HistoryItemViewUITests`, `KeyboardNavigationUITests`, `ListLiveScrollObserverIntegrationUITests`): run after the tag, results recorded in the next release note; two UI tests in that subset already fail on v0.76.0 (see v0.77.1).
- TSan, snapshot, and backend performance gates: not run; the search-index cache change is covered by the disk-cache hardening tests, no query, cleanup, or storage-schema code changed.

## Current Status

Hover, search, capture, launch and paging behave as before; the only visible differences are earlier previews at their final size and a list that no longer flashes empty while typing.

## Remaining / Next

- Per-keystroke work is now the layout of the result rows themselves (text, hosting cells); a page apply still costs two frames per chunk because SwiftUI diffs and re-initializes every ForEach child per update.
- The HTML importer still runs on the main thread when the stored text can depend on it (TeX-bearing or Markdown-authored copies).
- The panel's ~9% idle GPU (blur material, unverified) is untouched.
