# v0.73.0

## Summary

`v0.73.0` replaces the bundled `pngquant` binary with a build of the maintainer's fork of pngquant/libimagequant whose quantization engine runs 2.5-4x faster on all cores (histogram, palette selection, and dithering), with output that no longer depends on the number of threads or on the CPU architecture. Scopy's defaults, settings, UI, and the `PngquantService` contract are unchanged; speed 3 remains the default for both image capture and Markdown/LaTeX export because it matches speed 4 in time while producing slightly better palettes, and speed 1 costs 2x more for a fraction of a percent of error.

## Why This Release

Every captured image and every exported Markdown/LaTeX PNG that has compression enabled passes through the bundled `pngquant`. The previous binary was the official `3.0.3` release build. The engine work targeted the parts of libimagequant that were sequential or latency-bound: single-threaded color counting, one-box-at-a-time median cut, one dithering chunk per core with a slowest-chunk tail, and a nearest-color search that scanned the whole palette for far-off pixels. The visible per-image gain in the CLI is smaller than the engine gain (4-33% on real Scopy exports, up to 2x on screenshots) because PNG decoding and libpng's level-9 encoding are unchanged and dominate for large exports; that remains the next lever.

## Key Changes

### Bundled pngquant Engine

- `Scopy/Resources/Tools/pngquant` is now built from source: `kornelski/pngquant` `main` (`913a90d`, version string `3.0.4`) on the fork's `perf` branch (`af354ef`), with `ImageOptim/libimagequant` `main` (`9388d26`, 4.5.0) plus the fork's `perf` branch (`fddcf09`). Features `static cocoa`: static libpng and lcms2, Cocoa image reader, system `libz`, the same dependency footprint as the official build.
- Universal `arm64` + `x86_64` (the Intel slice is cross-built with `-Zbuild-std` and was verified under Rosetta), ad-hoc signed. Provenance and the exact rebuild commands live in `Scopy/Resources/ThirdParty/pngquant/PROVENANCE.md`.
- Engine changes on the fork: streaming row conversion and row-parallel contrast maps; a 64-partition parallel histogram with a canonical item order; median cut that precomputes split trees several levels deep with `rayon::join` and swaps buffers instead of copying back; dithering in 32-row chunks, eight per thread, two chunks interleaved per task; an exact SIMD neighbor-list nearest-color search with 16 hub lists for far-off pixels; best-palette guesses restored before k-means refinement; parallel palette finalization and dither maps.
- Determinism: median cut speculation runs even single-threaded, sums use fixed chunking, and the histogram order is canonical, so single-thread and all-thread outputs are byte-identical on the whole 58-output bench set, and the `x86_64` and `arm64` slices produce byte-identical files.

### Behavior Differences Against The Previous Binary

- Quality: on the fork's 4-image bench set (photo, photo with alpha, UI screenshot, 810k-color gradient noise; speeds 1/4/10, `--nofs`, `--posterize 2`, `--quality 60-80`) the MSE against the original is within -4.0%..+0.7% of unchanged upstream 4.5.0, mostly lower; no visible seams at dithering chunk borders in 4x crops.
- Sizes on real Scopy assets with Scopy's own arguments (`--quality 70-85 --speed 3 --skip-if-larger --strip 256 -`): most exports move by less than 1% (screenshot `50,315 -> 47,267` bytes; `chatgpt-public-copy.png` `1,846,896 -> 1,846,983`); two exports the old binary skipped as "larger" now compress (`link-enrichment-e2e.png` `97,038 -> 26,699`; `public-copy-with-adapters.png` `2,592,990 -> 648,541`); `pub-images.png` and `v2-finance.png` grow 2.6% and 2.0%.
- One difference inherited from upstream 4.5.0, not from the speed work (verified against an unchanged 4.5.0 build): an image whose colors already fit the palette can be reduced by one color and dithered when the quality maximum is below 100. For an already 4-bit-indexed export this made the result larger than the input, so `--skip-if-larger` returned exit 98 and Scopy kept the original bytes (`630,614` instead of the old binary's `621,724`). The same content as a 24-bit input compresses to `608,912` bytes, 2% smaller than the old binary's result.

## Verification And Performance

Engine, same harness, min of 5 runs, Apple M3 Pro (5P+6E), macOS 15.7.3, rustc 1.98.0:

| Image | Speed 1 | Speed 3 | Speed 4 | Speed 10 |
| --- | ---: | ---: | ---: | ---: |
| photo 2048x2048 | `269 -> 131ms` (2.06x) | `117 -> 37ms` (3.15x) | `115 -> 37ms` (3.11x) | `62 -> 23ms` (2.68x) |
| UI 2560x1600 | `187 -> 85ms` (2.20x) | `114 -> 39ms` (2.94x) | `101 -> 33ms` (3.05x) | `45 -> 16ms` (2.82x) |
| photo with alpha | `210 -> 81ms` (2.59x) | `138 -> 35ms` (3.92x) | `121 -> 30ms` (3.98x) | `47 -> 12ms` (3.88x) |
| gradient noise 1024x1024 | `332 -> 119ms` (2.79x) | `239 -> 68ms` (3.50x) | `183 -> 52ms` (3.55x) | `63 -> 16ms` (3.95x) |

Per stage at speed 3: histogram 3.2-6.8x, palette selection 3.3-4.2x, dithered remap 2.4-4.2x; single-threaded pipeline 1.35-1.83x. Speed 1 gains less because it keeps dithering single-threaded by design.

Whole CLI on real Scopy assets, old official `3.0.3` build vs this build, min of runs: screenshot `1216x838` `0.08 -> 0.06s`; `user-markdown-stress.png` `2160x138038` `36.26 -> 35.98s`; `chatgpt-public-copy.png` `2.52 -> 2.38s`; `rich-surfaces-all-types.png` `3.11 -> 3.00s`; `scopy_uitest_export_rich_markdown.png` `0.59 -> 0.55s`. The engine is now a few percent of those times; libpng encoding is the rest.

- The bundled tool inside the built app bundle was executed directly (`--version` on both architectures, and a compression round trip with Scopy's arguments).

## Current Status

Scopy behaves as before with a faster, deterministic quantizer underneath. Settings defaults (speed 3, quality 65-80 for captured images, 70-85 for exports, 256 colors) are unchanged and remain the recommended balance.

## Remaining / Next

- Whole-file latency for large exports is bound by libpng level-9 encoding in the CLI, not by quantization; a faster deflate level for exports, or an encoder change in the fork, is the next lever.
- The fork's `perf` branches are the corresponding source for the GPL binary and should be published alongside the release.
- The Intel slice was verified under Rosetta on Apple silicon only.
