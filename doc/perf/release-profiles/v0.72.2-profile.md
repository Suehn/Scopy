# v0.72.2 Release Performance Profile

## Scope

This profile records the performance-sensitive parts of `v0.72.2`: non-blocking short-query fallback, explicit short-index readiness for steady-state measurement, removal of obsolete runtime profiling, and bounded preview/enrichment work. The release claims truthful phase separation and preserved SLOs, not a blanket speedup.

## Release Gate

The canonical Release gate measures three distinct phases instead of treating repeated warm-up queries as proof that an asynchronous index became ready:

| Workload | Layer / readiness | Samples | Result | Gate |
| --- | --- | ---: | ---: | ---: |
| `cmd`, fuzzy+ | service | 30 | p95 `0.682ms` | `<=50ms` |
| `cm`, fuzzy+ | engine, explicit `prepareShortQueryIndex()` | 30 | p95 `5.458ms` | `<=20ms` |
| `cm`, fuzzy+ | service, cold observation | 1 | `103.974ms` | observation only |

The cold row is one sample, not a percentile. It stays within the product's 100-150ms first-result envelope for a roughly 10k-item corpus but is deliberately not converted into a new arbitrary threshold.

## Same-Snapshot Diagnostic Comparison vs v0.72.1

For a bounded diagnostic, the tagged `v0.72.1` bench and the candidate ran identical service commands against the same SQLite `mode=ro&immutable=1` URI. This URI prevents mutation but also prevents the normal path-keyed short-index cache from being reused, so the table is a startup/build-contention stress observation rather than the release gate or a product-wide before/after claim.

| Workload | v0.72.1 | v0.72.2 candidate | Interpretation |
| --- | ---: | ---: | --- |
| `cmd`, 30 samples after 20 warm-ups, p95 | `0.630ms` | `1.314ms` | `+0.684ms`; absolute latency remains far below SLO |
| `cm`, first sample | `732.886ms` | `50.390ms` | single samples are order/page-cache sensitive; no causal percentage claim |
| `cm`, 30 samples after 20 warm-ups, p95 | `6.302ms` | `47.684ms` | candidate median was `6.119ms`, with temporary 47-68ms build-contention tail |

The tail is the intentional tradeoff of never waiting synchronously for the background index task: first queries use the bounded SQL fallback instead of risking the historical long cold stall. Once readiness is explicit, the canonical steady-state result is `5.458ms`. The diagnostic host was busy (load averages around 9-10), so no fine-grained percentage claim is made.

## Frontend Evidence Boundary

`make perf-frontend-profile` reached the XCUITest runner but failed before any product scenario with `Timed out while enabling automation mode`. The same environment also blocks the required full profile. No summary JSON or unified backend/frontend table exists for this candidate, so frontend performance is `environment-blocked`, not passed and not used for a speedup claim.

The affected frontend code is guarded instead by normal, strict-concurrency, TSan, focused preview-pipeline tests, and bounded permit-pool tests. This is functional/concurrency evidence, not a substitute frontend performance measurement.

## Test Coverage And Tooling Changes

- Performance tests run only under the performance gate; decorative always-true assertions and warning-only `PerformanceAssertions` are gone.
- `PerformanceProfiler.swift` (315 lines) and `PerformanceProfilerTests.swift` (246 lines) are removed; production no longer carries unused profiling state.
- Integration-only clipboard setting tests are separated from unit/strict suites and run by `make test-integration`.
- `ScopyBench --prepare-short-index` is engine-only and fails fast if combined with the service layer, preventing ambiguous benchmark setup.

## Regressions And Residuals

- No functional, correctness, concurrency, or sanitizer regression was identified.
- Early short-query fallback can show a temporary latency tail while the index is building; the product remains responsive because it does not await the build task.
- Frontend full-profile and unified-table evidence are absent due to the environment blocker above.
